(même plan que les chapitres 4 et 5 — coller dans RAPPORT-FINALE2.docx)


Introduction

Le parc est visible. Ce chapitre est consacré au troisième sprint de réalisation de WatchDesk. L’objectif est de traiter ce qui se passe après la collecte : ouvrir et suivre les incidents, alerter par e-mail si la gravité est critique, interroger l’assistant IA, consulter les vulnérabilités, puis, côté super administrateur, régler les seuils, les règles d’alertes, les comptes et le journal d’audit. Les alertes partent par e-mail (SMTP), pas par une messagerie d’équipe.

Cas d’utilisation « Gérer les incidents »

Un écart sur un poste (CPU, RAM, disque, etc.) devient un incident, sans recréer un doublon déjà ouvert du même type sur la même machine. L’administrateur en change ensuite le statut.

TABLEAU 6.2 — Description textuelle « Gérer les incidents »

Préoccupation	Description
Cas d’utilisation	Gérer les incidents
Acteur	Administrateur ou super administrateur. Agent Windows (déclenchement). Service SMTP (alerte)
Objectif	Créer, lister, filtrer et clôturer les incidents du parc
Préconditions	L’utilisateur est authentifié avec un rôle admin. Des machines reportent. Le mode maintenance est désactivé pour les créations automatiques.
Postconditions	Un incident a un statut (OUVERT, EN COURS, RÉSOLU). L’action est écrite dans l’audit. Si gravité critique, un e-mail a pu partir.
Scénario principal	1. L’agent envoie POST /api/agent/report. 2. L’API compare aux seuils. 3. S’il n’existe pas d’incident ouvert du même type sur la même machine, création (OUVERT). 4. Si gravité critique, e-mail SMTP. 5. L’administrateur ouvre Incidents (GET /api/incidents). 6. Il change le statut (PATCH /api/incidents/{id}/status).
Scénarios alternatifs	A1. Incident déjà ouvert du même type → pas de doublon. A2. Mode maintenance → pas de création automatique. A3. Lecture seule → consultation limitée, pas de changement de statut.


Cas d’utilisation « Interroger l’assistant IA »

L’assistant aide à lire le parc ou un incident. Il ne décide pas à la place de l’administrateur. L’appel Gemini passe uniquement par le backend.

TABLEAU 6.3 — Description textuelle « Interroger l’assistant IA »

Préoccupation	Description
Cas d’utilisation	Interroger l’assistant IA
Acteur	Administrateur ou super administrateur. API Gemini
Objectif	Obtenir une réponse contextualisée (machines, incidents, CVE)
Préconditions	L’utilisateur n’est pas en lecture seule. L’API Gemini est configurée. Un contexte parc/incidents peut être chargé.
Postconditions	Le texte s’affiche. L’événement CHAT_ASK est journalisé dans l’audit.
Scénario principal	1. L’administrateur saisit une question. 2. POST /api/chat/ask. 3. L’API charge le contexte dans PostgreSQL. 4. Elle envoie question + contexte à Gemini. 5. Elle journalise CHAT_ASK. 6. La console affiche la réponse.
Scénarios alternatifs	A1. Lecture seule → panneau chat absent. A2. Gemini indisponible → message d’erreur, pas de session cassée.


Cas d’utilisation « Suivre les vulnérabilités »

La page s’appuie sur l’inventaire logiciel et les correctifs remontés par l’agent. Elle est accessible en lecture.

TABLEAU 6.4 — Description textuelle « Suivre les vulnérabilités »

Préoccupation	Description
Cas d’utilisation	Suivre les vulnérabilités
Acteur	Lecture seule, administrateur ou super administrateur
Objectif	Voir les CVE, logiciels concernés et correctifs Windows
Préconditions	L’utilisateur est authentifié. L’agent a déjà envoyé un inventaire.
Postconditions	La liste (ou un résumé) des vulnérabilités est affichée.
Scénario principal	1. L’utilisateur ouvre Vulnérabilités. 2. GET /api/vulnerabilities. 3. Affichage des CVE, logiciels, correctifs.
Scénarios alternatifs	A1. Inventaire vide → page sans CVE, sans erreur.


Cas d’utilisation « Configurer le système »

Les seuils (CPU, RAM, disque), l’intervalle de heartbeat, le mode maintenance et le test d’e-mail se règlent ici. Page réservée au super administrateur.

TABLEAU 6.5 — Description textuelle « Configurer le système »

Préoccupation	Description
Cas d’utilisation	Configurer le système
Acteur	Super administrateur
Objectif	Régler les paramètres globaux de supervision et d’alerte
Préconditions	Rôle SUPER_ADMIN. Session valide.
Postconditions	Les nouveaux seuils / le heartbeat / le mode maintenance sont enregistrés. Un e-mail de test peut avoir été envoyé.
Scénario principal	1. Le super administrateur ouvre Configuration. 2. GET /api/configuration. 3. Il modifie seuils, heartbeat ou maintenance. 4. PUT /api/configuration. 5. Option : test d’e-mail (POST /api/configuration/test-email).
Scénarios alternatifs	A1. Compte lecture ou admin simple → page absente du menu. A2. Maintenance activée → plus de création automatique d’incidents.


Cas d’utilisation « Gérer les administrateurs »

Les comptes ne s’inscrivent pas seuls. Le super administrateur crée, active ou désactive, et attribue le rôle.

TABLEAU 6.6 — Description textuelle « Gérer les administrateurs »

Préoccupation	Description
Cas d’utilisation	Gérer les administrateurs
Acteur	Super administrateur
Objectif	Créer et piloter les comptes d’accès à la console
Préconditions	Rôle SUPER_ADMIN. L’inscription publique reste fermée.
Postconditions	Un compte existe avec un rôle (LECTURE ou ADMIN) et un état (actif / désactivé).
Scénario principal	1. Le super administrateur ouvre Administrateurs. 2. Il saisit nom, e-mail, mot de passe, rôle. 3. POST de création. 4. Il peut désactiver un compte ou changer le rôle.
Scénarios alternatifs	A1. Autre rôle → page absente. A2. Compte désactivé → plus de connexion (sprint 1).


Conception

Le diagramme de classes global est au chapitre 2. Ici, les classes concernées sont surtout Incident, les règles d’alertes, User (comptes) et les traces d’audit. Deux séquences détaillent les échanges les plus denses : création d’incident avec déduplication et e-mail, puis assistant IA.

Diagramme de séquence « Incident et alerte e-mail »

Chaque rapport agent est comparé aux seuils. L’API cherche un incident déjà ouvert du même type sur la même machine. S’il n’y en a pas, elle crée un incident OUVERT ; si la gravité est critique, un e-mail part via SMTP. L’administrateur liste ensuite les incidents et en change le statut ; la mise à jour est écrite dans l’audit. En mode maintenance, ces créations automatiques sont coupées.

Conclusion

Ce sprint a permis d’étudier et de réaliser la boucle d’exploitation de WatchDesk. Un écart sur un poste devient un incident, sans doublon inutile ; un e-mail part si c’est critique ; l’administrateur suit les statuts ; l’assistant IA aide à lire le parc, sans y accéder en lecture seule ; les vulnérabilités s’affichent à partir de l’inventaire ; le super administrateur pilote seuils, règles, comptes et traces.

WatchDesk est alors utilisable de bout en bout : on entre (sprint 1), on voit le parc (sprint 2), on traite ce qui dérape (sprint 3). Le chapitre suivant est consacré à la validation, aux tests et au bilan du stage.
