4.1 Introduction

Ce chapitre est consacré au premier sprint de réalisation de WatchDesk. L’enjeu est de poser la porte d’entrée de la console : sans authentification fiable, le parc, les actions distantes et l’administration des comptes n’ont pas de sens. L’objectif est qu’un utilisateur s’identifie (e-mail et mot de passe, ou compte Google déjà autorisé), confirme son identité par un second facteur, puis entre avec un rôle limité (lecture, administrateur ou super administrateur) et une session limitée dans le temps. La création des comptes, l’agent Windows et les incidents sont reportés aux sprints suivants.

4.3.2 Cas d’utilisation « S’authentifier »

Tout utilisateur autorisé doit s’identifier avant d’ouvrir la console. Le mot de passe n’est jamais stocké en clair (hash BCrypt). Si le compte n’existe pas, s’il est désactivé ou si le mot de passe est faux, aucun jeton n’est délivré.

TABLEAU 4.2 — Description textuelle du cas d’utilisation « S’authentifier »

Préoccupation	Description
Cas d’utilisation	S’authentifier
Acteur	Lecture seule, administrateur ou super administrateur
Objectif	Ouvrir la console WatchDesk avec une session contrôlée
Préconditions	Un compte a déjà été créé par le super administrateur. La 2FA du compte est déjà activée (cas du quotidien).
Postconditions	Un JWT de 24 h est délivré. La console s’ouvre. Le menu correspond au rôle.
Scénario principal	1. L’utilisateur saisit son e-mail et son mot de passe.
2. La console envoie POST /api/auth/login.
3. L’API recherche le compte et vérifie le hash BCrypt.
4. L’API demande le code 2FA.
5. L’utilisateur saisit le code TOTP à 6 chiffres.
6. L’API contrôle le code, délivre le JWT (rôle + nom) et ouvre la console.
Scénarios alternatifs	A1. E-mail inconnu ou mot de passe faux → 401, message d’erreur, pas de jeton.
A2. Compte désactivé → 403, pas de jeton.
A3. Code 2FA faux ou périmé → accès refusé, pas de jeton.

4.3.3 Cas d’utilisation « Se connecter avec Google »

Google sert de second moyen de connexion, pas d’inscription ouverte. Seul un e-mail déjà présent dans WatchDesk est accepté. La suite (2FA, JWT) est la même que pour le mot de passe.

TABLEAU 4.3 — Description textuelle du cas d’utilisation « Se connecter avec Google »

Préoccupation	Description
Cas d’utilisation	Se connecter avec Google
Acteur	Lecture seule, administrateur ou super administrateur
Objectif	S’authentifier sans resaisir le mot de passe WatchDesk, avec un compte Google déjà autorisé
Préconditions	L’e-mail Google existe déjà dans la table des utilisateurs. Le compte est actif.
Postconditions	Après validation 2FA, un JWT est délivré et la console s’ouvre.
Scénario principal	1. L’utilisateur clique sur le bouton Google.
2. Google renvoie un jeton d’identité.
3. La console envoie POST /api/auth/google.
4. L’API vérifie le jeton auprès de Google et cherche l’e-mail dans WatchDesk.
5. La 2FA est demandée, puis le JWT est délivré.
Scénarios alternatifs	A1. E-mail Gmail absent de WatchDesk → 403, accès refusé.
A2. Compte désactivé → 403.
A3. Jeton Google invalide ou expiré → 401.

4.3.4 Cas d’utilisation « Activer la 2FA »

Ce cas n’a lieu qu’une fois par compte, tant que le téléphone n’est pas encore lié. Un QR affiché puis abandonné ne lie pas le compte : le secret n’est enregistré qu’après le premier code de confirmation.

TABLEAU 4.4 — Description textuelle du cas d’utilisation « Activer la 2FA »

Préoccupation	Description
Cas d’utilisation	Activer la 2FA (scanner le QR)
Acteur	Lecture seule, administrateur ou super administrateur
Objectif	Lier une application d’authentification (TOTP) au compte
Préconditions	Les identifiants (ou Google) sont valides. La 2FA n’est pas encore activée sur le compte.
Postconditions	Le secret TOTP est enregistré. Les connexions suivantes demandent un code à 6 chiffres, sans QR.
Scénario principal	1. L’utilisateur se connecte avec des identifiants valides.
2. L’API constate que la 2FA n’est pas activée et génère un secret.
3. La console affiche le QR (URI otpauth).
4. L’utilisateur scanne le QR dans Google Authenticator (ou équivalent).
5. Il saisit le premier code à 6 chiffres.
6. L’API enregistre le secret, délivre le JWT et ouvre la console.
Scénarios alternatifs	A1. Code de confirmation faux → le secret n’est pas enregistré, 2FA non activée.
A2. Abandon avant confirmation → le compte reste sans 2FA liée.


4.4 Conception

Le diagramme de classes global de WatchDesk a été présenté au chapitre 2. Pour ce sprint, la classe concernée est essentiellement User (e-mail, mot de passe haché, rôle, compte actif, secret 2FA, dernière connexion). Nous détaillons ici les échanges, via deux diagrammes de séquence.

Cinq interlocuteurs apparaissent : l’utilisateur, la console React, l’API Spring Boot, PostgreSQL et l’application d’authentification. La console ne décide pas de l’accès : elle transmet. Spring Boot vérifie et interroge PostgreSQL. Le code TOTP est calculé sur le téléphone ; WatchDesk ne l’envoie jamais par SMS.

4.4.1 Diagramme de séquence « Connexion avec 2FA »

Ce scénario correspond à un compte dont la 2FA est déjà activée. C’est le cas le plus fréquent.

L’utilisateur saisit e-mail et mot de passe. La console appelle POST /api/auth/login. Le serveur cherche le compte. Si le hash BCrypt ne correspond pas, si l’e-mail est inconnu ou si le compte est désactivé, la chaîne s’arrête (401 ou 403), sans JWT.

Si les identifiants sont valides, le serveur demande le second facteur. L’utilisateur lit le code à 6 chiffres (renouvelé toutes les 30 secondes) et le saisit. Code faux ou périmé : refus. Code juste : JWT (e-mail, rôle, nom), valable 24 heures. La console stocke le jeton et ouvre l’espace de travail. Les appels suivants portent ce jeton dans l’en-tête Authorization. S’il expire, retour à la page de connexion.

La connexion Google ne change que la première étape (POST /api/auth/google). Ensuite : 2FA, puis JWT.

4.6 Conclusion

Ce sprint a permis d’étudier et de réaliser l’accès à WatchDesk. Un utilisateur s’identifie par e-mail et mot de passe, ou par un compte Google déjà présent dans le système ; il confirme son identité par un code TOTP ; la console ne s’ouvre qu’après délivrance d’un jeton JWT de vingt-quatre heures, et le menu dépend du rôle. L’inscription publique est fermée.

L’authentification, à elle seule, ne montre pas encore le parc. Une fois la session ouverte, il reste à faire apparaître les postes Windows, à lire leur état et à pouvoir agir dessus. Le chapitre suivant est consacré au sprint 2 : agent de collecte, aperçu, liste des ordinateurs, actions à distance et rapports.
