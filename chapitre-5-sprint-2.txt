Chapitre 5 — Le deuxième sprint : Agent, aperçu et parc
(même plan que le chapitre 4 — coller dans RAPPORT-FINALE2.docx)


Introduction

Une fois la connexion en place, il faut voir les postes et agir dessus. Ce chapitre est consacré au deuxième sprint de réalisation de WatchDesk. L’objectif est d’installer un agent Windows qui remonte périodiquement l’état de la machine, d’afficher ce parc dans la console (aperçu et liste des ordinateurs), de permettre une action à distance (redémarrage, arrêt, mise à jour) et d’exporter des rapports. Les incidents, les e-mails d’alerte et l’administration des comptes restent hors de ce sprint : ils sont traités au chapitre 6.

Cas d’utilisation « Consulter l’aperçu »

L’aperçu est la première page après connexion. Il résume le parc en quelques indicateurs, sans entrer dans le détail d’une machine.

TABLEAU 5.2 — Description textuelle « Consulter l’aperçu »

Préoccupation	Description
Cas d’utilisation	Consulter l’aperçu
Acteur	Lecture seule, administrateur ou super administrateur
Objectif	Obtenir une vue d’ensemble du parc (effectifs, alertes, charge)
Préconditions	L’utilisateur est authentifié. Au moins un agent a déjà envoyé un rapport, sinon les compteurs restent à zéro.
Postconditions	Les KPIs sont affichés. L’utilisateur peut naviguer vers Ordinateurs ou Incidents.
Scénario principal	1. L’utilisateur ouvre la console (page Aperçu). 2. La console appelle GET /api/computers (et les compteurs associés). 3. L’API lit PostgreSQL. 4. La console affiche les tuiles (en ligne, alerte, hors ligne, charge). 5. Un clic sur une tuile ouvre la page correspondante.
Scénarios alternatifs	A1. Aucune machine en base → aperçu vide, sans erreur. A2. Session expirée → retour à la page de connexion.


Cas d’utilisation « Superviser les ordinateurs »

La page Ordinateurs liste les postes connus. Le détail (journaux, logiciels, disques) s’ouvre sur un clic.

TABLEAU 5.3 — Description textuelle « Superviser les ordinateurs »

Préoccupation	Description
Cas d’utilisation	Superviser les ordinateurs
Acteur	Lecture seule (consultation), administrateur ou super administrateur
Objectif	Voir chaque poste : identité, ressources, dernière vue, statut
Préconditions	L’utilisateur est authentifié. Des machines existent si l’agent a déjà reporté.
Postconditions	La liste est à jour. Le détail d’une machine peut être consulté.
Scénario principal	1. L’utilisateur ouvre Ordinateurs. 2. GET /api/computers toutes les 10 s. 3. Affichage de la liste (nom, IP, CPU, RAM, statut). 4. Clic sur une ligne → détail (journaux, logiciels, disques).
Scénarios alternatifs	A1. Machine hors ligne (plus de heartbeat) → statut hors ligne. A2. Lecture seule → pas de boutons d’action.


Cas d’utilisation « Exécuter une action à distance »

L’ordre n’est pas poussé en temps réel vers le poste : l’agent le récupère à son prochain cycle (sondage). Une confirmation est exigée avant l’envoi.

TABLEAU 5.4 — Description textuelle « Exécuter une action à distance »

Préoccupation	Description
Cas d’utilisation	Exécuter une action à distance
Acteur	Administrateur / super administrateur. Agent Windows (exécution)
Objectif	Redémarrer, éteindre ou proposer une mise à jour Windows sans accès physique
Préconditions	L’utilisateur n’est pas en lecture seule. Le poste a déjà envoyé au moins un rapport. Confirmation saisie.
Postconditions	La tâche est enregistrée. L’agent l’exécute au poll suivant. Le statut du parc se met à jour au rapport suivant.
Scénario principal	1. L’administrateur choisit un PC et une action. 2. Il confirme. 3. POST /api/agent/trigger-action/{ip}. 4. L’API enregistre la tâche en attente. 5. L’agent appelle GET /api/agent/check-tasks/{ip}. 6. Il exécute l’ordre sur Windows. 7. Le rapport suivant met à jour la console.
Scénarios alternatifs	A1. Lecture seule → pas de boutons. A2. Agent arrêté → l’ordre reste en attente jusqu’au prochain poll. A3. Annulation de la confirmation → aucun ordre.


Cas d’utilisation « Générer des rapports PDF / Excel »

L’export se fait dans la console, à partir des données déjà chargées. Il ne relance pas une collecte agent.

TABLEAU 5.5 — Description textuelle « Générer des rapports PDF / Excel »

Préoccupation	Description
Cas d’utilisation	Générer des rapports PDF / Excel
Acteur	Lecture seule, administrateur ou super administrateur
Objectif	Exporter un état du parc pour archivage ou partage
Préconditions	L’utilisateur est authentifié. Des données parc sont disponibles.

Cas d’utilisation « Déployer l’agent Windows »

Sans agent, aucune machine n’apparaît. Le déploiement est réservé au super administrateur.

TABLEAU 5.6 — Description textuelle « Déployer l’agent Windows »

Préoccupation	Description
Cas d’utilisation	Déployer l’agent Windows
Acteur	Super administrateur. Agent Windows (après installation)
Objectif	Installer l’agent sur un poste pour l’intégrer au parc
Préconditions	L’utilisateur a le rôle SUPER_ADMIN. Le serveur WatchDesk est joignable depuis le poste.

Conception

Le diagramme de classes global est au chapitre 2. Ici, la classe concernée est surtout Computer (identité, ressources, dernière vue, statut). L’agent n’écrit pas dans une table « rapports » : chaque envoi met à jour la machine. Deux séquences décrivent les échanges : collecte puis affichage, et action à distance.

Diagramme de séquence « Collecte agent et affichage du parc »

L’agent lit CPU, RAM, disques et journaux Windows, puis envoie un JSON (POST /api/agent/report). L’API met à jour Computer dans PostgreSQL et répond 200. L’agent demande ensuite s’il a une tâche en attente (GET /api/agent/check-tasks/{ip}). Côté console, un appel GET /api/computers toutes les 10 secondes relit le parc et rafraîchit l’aperçu (en ligne, alerte, hors ligne).

FIGURE 5.2 — Diagramme de séquence : collecte agent et affichage du parc
Fichier : figures/fig-sprint2-sequence-collect.png

Diagramme de séquence « Action à distance »

L’administrateur choisit un poste et une action. La console appelle POST /api/agent/trigger-action/{ip}. L’API enregistre l’ordre et confirme tout de suite (« ordre enregistré ») : l’exécution n’est pas synchrone. Au poll suivant, l’agent récupère la tâche, l’exécute sur Windows, puis le rapport suivant met à jour le statut dans la console.

Conclusion

Ce sprint a permis d’étudier et de réaliser le lien entre les postes Windows et la console. Un agent collecte les métriques et les envoie à l’API ; l’aperçu et la page Ordinateurs affichent le parc ; une action à distance peut être déposée et exécutée au cycle suivant ; un rapport PDF ou Excel s’exporte depuis la console ; le super administrateur déploie l’agent.

Le parc est visible, mais un écart (CPU saturé, disque plein) ne produit pas encore d’incident ni d’e-mail. Le chapitre suivant est consacré au sprint 3 : incidents, notifications, assistant IA, vulnérabilités et administration.
